We ran SERV on our own agent before asking anyone to run it on theirs. These are the results, including the one that does not flatter SERV.

All runs below are on `gpt-6-luna`, 40 cases, run on 26 Sep 2026, SERV off against SERV on. SERV off is the model on its own. SERV on is plain mode: SERV's reasoning on, with its output filter off (Urai always switches it off so answers that quote the rules are not cut), nothing else added. Each agent went to SERV exactly as written, with its answer schema's fields in their original order.

## A well laid out agent: close to parity

The good-layout payables agent: rules in the system prompt, the supplier book in the user message.

| | SERV off | SERV on |
|---|---|---|
| Accuracy | 39 of 40, 97.5% | 37 of 40, 92.5% |
| Input tokens | 240,442 | 159,482 |
| Output tokens | 24,164 | 18,673 |
| Mean latency | 6.4 s | 5.3 s |

SERV on used 33% fewer tokens in total, input and output together, and got 2 fewer cases right than the model alone. The two settings disagreed on 4 of 40 cases. SERV on was also about a second faster per call.

That is a real trade: 33% fewer tokens for 5 points of accuracy on this agent. Whether it is worth it depends on what a wrong answer costs you. [Open the report](/r/l9eNk-PBGlRDmUnNIxzsxQ) and read the four cases.

## A hard rulebook: SERV scored far lower

The hard set: 152 clauses from four layered rule sources, where one missed exception flips a payment. Data in the user message, so the layout was right.

| | SERV off | SERV on |
|---|---|---|
| Accuracy | 39 of 40, 97.5% | 18 of 40, 45% |
| Input tokens | 617,829 | 274,389 |
| Output tokens | 34,049 | 36,477 |
| Mean latency | 8.8 s | 8.2 s |

SERV on used 52% fewer tokens and lost 52.5 points of accuracy. The settings disagreed on 21 of 40 cases. Our best explanation is the one behind the setup check's long-prompt note: SERV compresses the system prompt into its own reasoning graph, and a long, layered rulebook has the most detail to lose. We have not proven that case by case, so read the 21 cases yourself. [Open the report](/r/zTS-p-PZ_w8nRzVCCgHk1g).

## A bad layout: the mistake you can fix

The third result is about setup, not SERV itself. With the supplier book pasted into the system prompt, SERV on scored 67.5% while the model alone scored 97.5% on the same layout. So the mistake only hurts with SERV on. After the one-click fix moved the book to the user message, SERV on scored 97.5% against 100% with SERV off, and used 31% fewer tokens. See [Setup check](/docs/concepts/setup-check).

## What this means for your agent

SERV is not a switch that makes every agent better. On one agent it came within 5 points of the model alone and used 33% fewer tokens. On another it lost 52.5 points of accuracy. On a third, the result depended on where one block of data sat.

So test it on your own cases before you switch it on. Run SERV off against SERV on, the setting the builder calls SERV plain, on the same model, with the layout the setup check is happy with, and read the cases where they disagree. That is what Urai is for. Start on [/new](/new), or watch a run first on [/try](/try).
