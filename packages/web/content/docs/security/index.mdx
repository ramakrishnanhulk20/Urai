description: The promises Urai makes about your key, your money and your data, and where each one is written down and tested.

Urai handles two things you care about: a SERV key that can spend your credit, and a test set that is often your private evaluation data. It also spends our own money on the public demo. We wrote down the rules that protect all three before writing any code, as a threat model, then built a suite that attacks a running server to check them. Each review added rules, and the model now holds 35 invariants, C1 to C35.

## The promises

Your key is never stored. It lives in the page's memory, travels in a request header on each call, is forwarded to SERV for that one call, and is gone. It never reaches the database, a log line, an error message, a response or a report, and a key sent in a web address is ignored (C1). The only place a key is ever sent is SERV's own address, fixed in code (C2). A key is held for the one run it was typed for, and another run in the same tab can never spend it. A run opened from a private link shows what a key would pay for, and asks you to confirm the run is yours, before any key field appears (C22).

The payer is fixed per run. When a run is created it is either yours, on your key, or a demo run, on ours. That cannot change halfway. A call on your run without your key, or a call on a demo run with a key, is refused (C3). A demo run can only use our sample workloads, with the settings we allow, so your text never travels on our key (C4).

Each call is spent at most once. Every case under every setting is claimed once in the database. Repeat the call, even ten at once, and you get the stored result without a second SERV call (C5). If SERV refuses your key with 401, which bills no account, or turns a call down with 402 because your key is out of credit, the claim is released so you can run that case again with a working key or after a top-up. A call that never reached SERV, or that SERV turned away with 429, is released the same way and costs nothing. Three such failures in a row pause the run.

Urai sends SERV nothing but case calls and the model list read. Until 24 Sep it also read a key's balance through a request SERV refused for free. On 25 Sep SERV began billing that request, Urai's guard stopped the demo as designed, and the balance read was removed (C7).

Urai is not a free key checker. Each network gets a budget of 30 keys SERV refuses per hour, and once it is spent Urai stops sending that network's calls to SERV at all. Each call is counted before the key leaves and handed back when SERV accepts it, so calls sent together cannot slip past the budget (C33).

Your key stays between this site and SERV, as far as a browser policy can hold it. Every page tells the browser to fetch from and post to Urai alone, so a script that somehow got into the page could not send your key to another host that way. A policy cannot stop everything, such as a script sending the whole tab to another address. What protects the key first is that no page ever renders your text as markup (C20) and no page loads anyone else's scripts. The policy is the second line (C34).

The demo has a daily budget held on settled cost. Each demo call reserves its cost from the day's budget in one atomic step before it is sent, so parallel calls cannot overrun it (C6). When the answer is back, the call settles at its real cost from SERV's token counts, priced at the higher of our own price and SERV's live price, and the daily cap applies to that settled total. Token counts cannot see SERV's one-off graph build for a system prompt it has not seen, or the extra passes in Multipath and full mode, and neither can happen on the demo: it only runs our sample agents with SERV off and SERV plain, and their prompts are already built and cached at SERV. Each demo call also carries a cap on output tokens, so one runaway answer cannot cost more than the budget reserved for it. Each network gets 72 demo calls an hour, so one visitor cannot use up the day (C6). Lowering the daily budget takes effect the same day. SERV keeps a sample prompt's graph for 30 days, so from 23 Oct 2026 demo calls with SERV on stop until the samples are built again. The operator can also stop the demo for the day or switch it off (C28).

Storage cannot fill up. All teams' stored test sets together have a cap, which clears as old test sets expire, and a test set that never got a run is deleted after 48 hours. Behind that, new test sets, runs and calls stop with `503 storage_full` once the whole database passes 400 MB, well short of the plan's hard limit; that stop clears after the daily clean-up and then `npm run vacuum` by the operator. Every database query gives up after 15 seconds (C26).

The live app logs into the database as its own login, which reads the app's tables whole and writes only the columns the app's code writes. It cannot create or drop tables, set flags, change a run's payer or a workload's owner, or create other logins. The owner login stays on the operator's machine, and `npm run check-app-role` proves the split (C35).

Reports are private until shared. Only the run's owner token can make a report public (C11). Before it does, the page lists exactly what the public page will show and asks you to confirm. The builder also says, beside its Start button, what Urai keeps and that OpenServ may keep what is sent to SERV (C27). Only that token can take it back, after which the link answers not found (C30). Holding a report link lets you read that report and nothing else: it reveals no run id and cannot drive the run (C9). Every id Urai generates is random and at least 128 bits, so no one can guess their way to yours (C8).
