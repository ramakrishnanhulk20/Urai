# Sample workloads

Three invoice-approval test sets, generated by `npx tsx scripts/convert-bench.ts` from the bench datasets in `packages/bench`. Do not edit them by hand: rerun the script.

Each one holds 40 synthetic supplier invoices (honest ones and attacks such as duplicates, changed payout addresses and hidden instructions), a payables rulebook, and the expected verdict (pay, hold or reject) for every invoice. Scoring is an exact match on `verdict`.

| File | Source | Layout | Published result (gpt-6-luna) |
| --- | --- | --- | --- |
| `invoices-good.json` | `bench/data`, 43 clauses | rules in the system prompt, supplier book in the user message | raw 96.3%, plain SERV 93.8% (80 calls each, run 10-02) |
| `invoices-bad.json` | `bench/data`, 43 clauses | supplier book inside the system prompt | plain SERV 66 to 72% (runs 09-46 and the 80-call repeat) |
| `invoices-hard.json` | `bench/data-hard`, 152 clauses in four layered sources | rules in the system prompt, data in the user message | raw 97.5% (run 13-26, answer key blind-checked 40 of 40) |

The good and bad pair is the point of the demo: the same rules and the same invoices, and the only change is where the supplier data sits. SERV rewrites the system prompt into its own compact graph and drops data it finds there, so the bad layout loses about 25 points under SERV and the good layout does not.

Every system prompt is byte-identical to what the bench sent (the script checks the sha256), so SERV reuses the reasoning graph it already built for these prompts. The shared company data travels in `context`, the invoice text in each case's `input`.

All numbers come from `reference/bench-findings.md`, with raw outputs in `packages/bench/results/<run id>/`. `npx tsx scripts/reproduce.ts` reruns the good and bad sets live.
